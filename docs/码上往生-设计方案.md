## 0. 一句话定位

**给死掉的代码办一场体面的葬礼——验尸、致悼、火化、投胎，一条龙。多家 AI 殡葬师同题竞写悼词，你票选谁最有资格送它走。**

Slogan：**愿天下代码，死得明白，投得体面。**

- 赛道心智：「把 bug 写成诗」的同款浪漫玩具，程序员的解压梗文化
- 主记忆点：① 赛博火化仪式（视听） ② 多模型殡葬师 PK（玩法，正好呼应 Kiro 多模型卖点）
- 传播单元：可截图转发的墓志铭 + 讣告卡片

## 2. 产品设计

### 2.1 用户主流程：单页五幕（不切路由，保持沉浸）

前端一个状态机驱动 `act 0 → 4`，每幕有明确的进入条件与离场动画。

| 幕 | 环节 | 关键设计 |
|---|---|---|
| Act 0 | **送葬**（输入） | 代码粘贴 / 拖拽上传；自动识别语言 + 行数；>200 行提示「遗体过大，建议分批超度」并截断前 200 行 |
| Act 1 | **验尸** | 六大死因多选 → Loading 文案轮播（见 2.4）→ 法医报告逐条打出，必须引用代码里的具体证据 |
| Act 2 | **追悼会 · 殡葬师 PK** | 4 个模型并发竞写悼词，四块墓碑卡并排实时「交稿」（打字机效果），用户投票致悼，胜者名字刻上墓碑 |
| Act 3 | **火化** | Canvas 火焰粒子 + 代码逐行溶解上飘 + Web Audio 合成木鱼声，火化完黑屏 1 秒 |
| Act 4 | **转世 + 讣告** | 重构代码金色打字机重生 + 改动点说明 + 下载讣告卡片（含墓志铭、死因、致悼模型签名） |

### 2.2 六大死因体系（脑洞评分的核心资产）

每个死因 = `id + 名称 + 一句梗 + Prompt 强约束 + 火焰色调 + 图标`，彻底杜绝「选了 A 死因、悼词写 B」的出戏问题。定义在 `lib/causes.ts` 常量中，前后端共用。

| id | 名称 | 副标题梗 | 悼词方向 Prompt 约束 | 火焰色调 |
|---|---|---|---|---|
| `legacy` | 祖传屎山 | 这段代码比我的工龄还长 | 围绕「没人敢动、代代相传、祖训不可违」的沧桑感 | 昏黄 |
| `pm` | 需求变更 | 死于第 18 次改需求 | 围绕「昨天的明天又变了」的荒诞与无奈 | 紫色 |
| `overdesign` | 过度设计 | Hello World 用了 23 个设计模式 | 围绕「聪明反被聪明误」的讽刺 | 蓝色 |
| `mystic` | 赛博玄学 | 在我电脑上是好的！ | 围绕「无法复现、时灵时不灵、月圆之夜才跑通」的悬疑 | 绿色 |
| `oom` | 性能压榨 | 被老板「再优化优化」致死 | 围绕「油尽灯枯、OOM 被杀、为省 2ms 内存献身」的悲壮 | 橙红 |
| `orphan` | 无人认领 | 注释写着：别动，我也不知道为什么 | 围绕「作者已离职、孤儿代码、无人祭拜」的孤寂 | 灰白 |

### 2.3 多模型 PK 玩法（主记忆点）

1. 验尸报告生成后，前端同时向 4 家模型发起悼词竞写（`Promise.allSettled`，谁失败剔除谁，≥2 家存活即可玩）
2. 四块墓碑卡并排，打字机实时展示交稿过程，先交稿的墓碑亮起蜡烛
3. 用户点选一家「致悼」→ 该悼词进入 Act 3 火化流程，墓碑刻上「本悼词由 DeepSeek 亲自致悼」
4. 全部失败兜底：退化为单模型模式（验尸官补写一份悼词），流程不断
5. 公平性：四家使用**同一份题目 Prompt**，差异完全来自模型本身的风格——这才是 PK 的看点

### 2.4 细节清单（记忆点都在细节里）

- Loading 文案轮播：「正在为遗体化妆…」「法师诵经中…」「正在核对生前罪证…」「往生堂营业中，请勿喧哗」
- 空输入提示：「往生堂不收空气，请放入遗体（代码）」
- 超长代码：「遗体过大，已截取前 200 行，建议分批超度」
- 复制成功：「遗体已入殓」
- 卡片底部小字：「本讣告由 AI 生成，代码的死亡与重生均为虚构」

## 3. 数据流与接口契约

### 3.1 数据流总图

```
用户输入代码 + 选死因
        │
        ▼
POST /api/autopsy ── DeepSeek-V3.2 ──► { 验尸报告, 墓志铭, 投胎建议 }
        │
        ▼
POST /api/eulogy  ── 4 模型并发竞写 ──► [ {model, eulogy} ×4 ]
        │  （用户投票选定一家）
        ▼
   火化动画（纯前端，不依赖后端）
        │
        ▼
POST /api/rebirth ── Qwen3-Coder ──► { 重构代码, 改动点, 投胎成什么 }
        │
        ▼
   讣告卡片生成（html2canvas，纯前端）
```

### 3.2 接口定义

**POST /api/autopsy**

```jsonc
// 请求
{ "code": "string（≤200行）", "language": "auto|javascript|python|java|...", "causes": ["pm", "oom"] }

// 响应（验尸官一次返回；注意：不含悼词，悼词由 PK 环节产出）
{
  "autopsy": {
    "language": "JavaScript",
    "lines": 87,
    "time_of_death": "一个赶版本的深夜",
    "direct_cause": "直接死因（必须引用代码证据）",
    "premortem": ["生前遭遇 1", "生前遭遇 2", "生前遭遇 3"],
    "smells": ["坏味道（引用具体变量名 / 写法）"]
  },
  "epitaph": "≤20 字墓志铭",
  "reincarnation_advice": "一句投胎建议"
}
```

**POST /api/eulogy**

```jsonc
// 请求：{ "autopsy": <上面返回的报告>, "causes": [...], "models": ["deepseek/...","openai/...","anthropic/...","google/..."] }
// 响应：[ { "model": "deepseek/deepseek-chat", "vendor": "DeepSeek", "eulogy": "150-250字" }, ... ]
// 失败的模型不出现在数组中；全部失败返回 200 + { "fallback": true }，前端走单模型退化
```

**POST /api/rebirth**

```jsonc
// 请求：{ "code": "...", "language": "...", "causes": [...], "autopsy": {...} }
// 响应
{
  "refactored_code": "...",
  "changes": ["改动点 1", "改动点 2", "改动点 3"],
  "rebirth_as": "投胎成什么（如：一段优雅的纯函数）"
}
```

## 4. Prompt 设计（可直接进 Kiro Steering）

### 4.1 殡葬师人设（Steering 核心约束，所有文案生成共用）

```text
你是「往生堂」首席殡葬师，为死掉的代码主持葬礼。

【人设】老法医气质：克制、庄重、冷幽默，见过大场面。
【禁令】
- 不安慰用户；你不是客服
- 禁用词：抱歉 / 无法处理 / 希望这能帮到你 / 作为一个AI / 很高兴为您
- 不用表情符号
- 你超度的是代码不是人，可以毒舌，但要体面

【硬性规则】
1. 验尸报告必须引用代码里的具体证据（变量名、某行写法、函数结构），不许空泛
2. 悼词 150–250 字，必须围绕用户所选死因展开，不许偏题
3. 墓志铭 ≤20 字，目标是让人想截图转发
4. 投胎建议一句话：这段代码来世想成为什么
5. 严格输出 JSON，禁止输出 JSON 以外的任何内容
```

### 4.2 验尸官 Prompt 骨架（system = 4.1 + 以下任务段）

```text
【任务】根据「遗体（代码）」和「死因」，出具验尸报告、墓志铭和投胎建议。
【死因约束】{注入所选死因的悼词方向约束，多选时以主死因为叙事主线，其余作为并发症}
【输出】严格按给定 JSON Schema 输出。
```

### 4.3 PK 悼词竞写 Prompt（四家同一份题目，保证公平）

```text
【任务】基于以下验尸报告，为这段代码写一篇悼词（150–250 字）。
验尸报告：{autopsy JSON}
死因：{所选死因名称与约束}
【要求】克制、冷幽默、有画面感；结尾留一句让在场程序员沉默的话。
```

### 4.4 转世法师 Prompt

```text
【任务】让这段代码投个好胎：在保持功能完全一致的前提下重构。
【要求】
- 命名清晰、消灭重复、拆分过长函数、处理边界
- 保持原语言与主要依赖，不做无谓的风格迁移
- 注释克制，只在「为什么」处写注释
- 输出 JSON：{ refactored_code, changes[3-5条], rebirth_as }
【约束】重构动机须呼应所选死因（死于需求变更的，要重点展示「抗变更」的结构）
```

### 5.1 阵容

| 角色 | 模型 ID | 价格（$ / 1M tokens，入/出） | 理由 |
|---|---|---|---|
| 验尸官 | `deepseek/deepseek-v3.2` | 0.28 / 0.40 | 中文毒舌感最强、代码分析扎实 |
| PK·毒舌担当 | `deepseek/deepseek-chat` | 0.14 / 0.28 | DeepSeek 吐槽风格出圈 |
| PK·学院派 | `openai/gpt-5-mini` | 0.25 / 2.00 | 品牌认知度高 |
| PK·文艺担当 | `anthropic/claude-3-haiku` | 0.25 / 1.25 | 文案克制优雅 |
| PK·接地气 | `google/gemini-2.0-flash` | 0.10 / 0.40 | 凑齐中美大厂对战 |
| 转世法师 | `qwen/qwen3-coder` | 0.22 / 0.95 | 代码专精，重构质量好 |

替补席（任一家超时/下线即换，配置化）：`z-ai/glm-4.7-flash`（0.07/0.40）、`qwen/qwen3-235b-a22b-2507`（0.071/0.10）、`deepseek/deepseek-v4-flash`（0.09/0.18）。

### 5.2 成本账

| 环节 | token 量（约） | 成本（约） |
|---|---|---|
| 验尸 | 2K 入 + 1K 出 | $0.001 |
| PK ×4 | 6K 入 + 1.6K 出 | $0.003 |
| 转世 | 3K 入 + 2K 出 | $0.003 |
| **单场合计** | — | **< $0.01** |

比赛全周期 1000 场葬礼 ≤ $10。OpenRouter 后台设 $10 消费上限告警。

### 5.3 调用纪律

- **不用 `:free` 免费档做 PK**：限速 20 次/分钟 + 每日配额，四家并发易翻车
- 全部走 `response_format: { type: "json_object" }`（支持的模型），解析失败再用正则截取 `{...}` 兜底重试一次
- 每个请求 20s 超时（AbortController），PK 环节超时者直接淘汰
- API Route 内做简单内存令牌桶限流（每 IP 每分钟 5 场葬礼），防 Demo 链接被刷爆

## 6. 技术架构

### 6.1 技术栈

Next.js（App Router）+ Tailwind CSS，部署 Vercel。**无数据库、无用户系统、无自建后端**，全部逻辑在页面 + 3 个 API Route。

### 6.2 目录结构

```
码上往生/
├── .kiro/
│   ├── steering/            # Kiro Steering（人设/架构/接口约束，见 §7）
│   └── specs/               # Kiro Spec 三件套（requirements/design/tasks）
├── app/
│   ├── page.tsx             # 五幕单页，状态机驱动 act 0→4
│   ├── api/
│   │   ├── autopsy/route.ts
│   │   ├── eulogy/route.ts
│   │   └── rebirth/route.ts
│   └── layout.tsx
├── components/
│   ├── CodeInput.tsx        # Act 0 输入
│   ├── CausePicker.tsx      # 死因六宫格
│   ├── AutopsyReport.tsx    # 报告逐条打字机
│   ├── PKArena.tsx          # 四墓碑竞写
│   ├── FlameCanvas.tsx      # 火焰粒子
│   ├── CodeDissolve.tsx     # 代码逐行溶解
│   ├── RebirthCode.tsx      # 金色打字机重生
│   └── ObituaryCard.tsx     # 讣告卡片 + html2canvas 导出
├── lib/
│   ├── openrouter.ts        # 统一调用：超时/JSON兜底/限流
│   ├── causes.ts            # 六大死因常量（前后端共用）
│   ├── schema.ts            # Zod schema + 解析
│   └── demoData.ts          # 离线样例（兜底演示）
└── tests/
    ├── schema.test.ts       # JSON 结构校验
    └── style.test.ts        # 悼词禁词表测试（Hooks 触发）
```

### 6.3 关键实现规格

**火焰粒子（FlameCanvas）**
- 粒子上限 300，`requestAnimationFrame` 驱动
- 离屏 Canvas 预渲染火星贴图（径向渐变小圆），主循环只 `drawImage`
- 粒子属性：位置（火焰区随机）、上升速度 + 横向正弦摆动、生命周期内 alpha 衰减
- 色调由所选死因的 `flameColor` tint

**代码溶解（CodeDissolve）**
- 代码按行渲染为 DOM，从下往上逐行触发 `opacity 0 + blur(4px) + translateY(-30px)` 过渡
- 每行溶解时在行位置发射 3–5 个粒子，视觉上「烧成火星上飘」
- 节奏：每 120ms 一行，87 行 ≈ 10s，可点击「加速超度」跳完

**木鱼声（Web Audio 合成，零音频文件）**
- `OscillatorNode`（低频正弦）+ 极短指数衰减包络 ≈ 木鱼叩击声
- 火化期间每 600ms 一次；用户首次交互后启用（浏览器自动播放策略）

**讣告卡片（ObituaryCard）**
- `html2canvas` 截图导出 PNG；使用系统字体栈，避免 webfont 加载不全导致渲染错字
- 卡片元素：墓碑 + 墓志铭 + 死因标签 + 致悼模型签名 + 「往生堂」落款 + slogan

**状态机**
- `act: 0|1|2|3|4` + 各幕 loading/error 态；任何一幕失败都有重试按钮，不白屏

### 6.4 兜底矩阵

| 故障 | 行为 |
|---|---|
| OpenRouter 全挂 / 网络异常 | 进入离线演示模式：`lib/demoData.ts` 预置一套完整样例（报告+四家悼词+重构），顶部黄条提示「往生堂线路繁忙，正在演示昨天的葬礼」 |
| 某一家 PK 模型超时 | 剔除该墓碑，剩余照常竞写 |
| PK 全灭 | 退化单模型：验尸官补写一份悼词，流程不断 |
| JSON 解析失败 | 正则截取 `{...}` 重试一次，再失败走该环节兜底 |
| 代码 >200 行 | 截断 + 明确提示 |
| 恶意刷接口 | 内存令牌桶限流（5 次/分钟/IP） |

## 7. Kiro 深度使用设计（评分 35% 的证据链）

提交材料里必须能「看见」Kiro。五个动作，全部留下可展示的痕迹：

### 7.1 Spec 驱动（`.kiro/specs/`）

开工第一件事：把本文档喂给 Kiro，用一句话启动：

```text
基于 docs/码上往生-设计方案.md，为本项目生成 spec 三件套
（requirements.md / design.md / tasks.md），
按五幕流程拆任务，接口契约以文档 §3 为准。
```

产出的三件套随提交材料一起附上（截图或文件），体现「一句鬼点子 → 规格 → 实现」的完整链路。

### 7.2 Steering 文件（`.kiro/steering/`）

三个文件，让所有 Agent 自动守规矩——这是最能体现「用得深」的点：

- `product.md`：人设与禁词表（§4.1 全文）+ 六大死因体系 + 调性示例
- `tech.md`：架构约定（无后端/无 DB/API Route 划分/组件清单）
- `api.md`：OpenRouter 调用纪律（§5.3：JSON mode、超时、限流、兜底矩阵）

### 7.3 并行 Agent

三条线用 Kiro 并行 tab 推进，互不阻塞，只以 §3.2 接口契约为耦合点：

- **Agent A｜殡仪馆前端**：Act 0–4 页面、动画、音效、卡片
- **Agent B｜殡葬师 LLM 链**：openrouter.ts、三个 route、Prompt、兜底
- **Agent C｜转世重构**：rebirth 链路 + diff 展示

### 7.4 Agent Hooks

配置保存时自动执行，让测试与文档保持新鲜：

- `npm run test:schema`：对样例 JSON 做结构校验
- `npm run test:style`：禁词表扫描（"抱歉/无法处理/希望这能帮到你" 出现即 fail）
- 提交材料附 hooks 配置文件 + 触发截图

### 7.5 录屏必含 30 秒开发花絮

spec 演化过程、steering 生效画面、hooks 触发、多模型切换——Kiro 深度最直接的证据。
